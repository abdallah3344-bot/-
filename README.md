# نظام إدارة مكتب المحاماة

نظام متكامل لإدارة القضايا والعملاء والجلسات والمستندات والشؤون المالية
لمكاتب المحاماة في فلسطين.
عربي بالكامل، RTL، بواجهة حديثة ووضع ليلي، وقاعدة بيانات PostgreSQL حقيقية مع صلاحيات دقيقة.

---

## التقنيات

| الطبقة | التقنية |
|---|---|
| الإطار | Next.js 16 (App Router, Server Actions) |
| اللغة | TypeScript — وضع `strict` |
| التنسيق | Tailwind CSS v4 |
| المكوّنات | shadcn/ui (منسوخة داخل المستودع) |
| قاعدة البيانات | PostgreSQL 17 عبر Supabase |
| المصادقة | Supabase Auth — bcrypt + JWT + كوكيز HttpOnly |
| الصلاحيات | RBAC على مستويين: RLS في القاعدة + فحص في الخادم |
| الرسوم البيانية | Recharts |


## الأمان

الحماية على ثلاث طبقات مستقلة — تجاوز واحدة لا يكفي للوصول للبيانات:

1. **`proxy.ts`** — يمنع أي مسار محمي بدون جلسة صالحة.
2. **`requirePermission()`** — يتحقق من الصلاحية في الخادم قبل تنفيذ أي استعلام.
3. **سياسات RLS** — داخل PostgreSQL نفسها، تُصفّي الصفوف حسب الدور.
   المحامي لا يرى إلا القضايا المسندة إليه، وينتشر هذا القيد تلقائيًا إلى
   الجلسات والمستندات والمهام والفواتير المرتبطة بها.

إجراءات إضافية مطبَّقة:

- كلمات المرور مشفّرة بـ bcrypt داخل `auth.users` ولا تمرّ عبر جداول التطبيق.
- الجلسة في كوكيز `HttpOnly` — غير قابلة للقراءة من JavaScript.
- **منع تعداد الحسابات:** دالة `resolve_login_email` لا تكشف البريد المقابل
  لاسم المستخدم إلا بعد التحقق من كلمة المرور نفسها.
- الدور المجهول (`anon`) ممنوع من تنفيذ أي دالة داخلية.
- المستندات في حاوية تخزين **خاصة** — لا وصول مباشر، والتحميل عبر روابط
  موقّعة مؤقتة فقط.
- كل عملية حسّاسة تُكتب في `audit_logs` مع المستخدم والوقت والتغييرات.
- الحذف ناعم (`deleted_at`) — لا فقد لبيانات قانونية.

### إعداد يدوي مطلوب

فعّل **حماية كلمات المرور المسرّبة** من لوحة Supabase:
`Authentication ← Policies ← Leaked password protection`.
يمنع هذا استخدام كلمات مرور ظهرت في تسريبات معروفة، ولا يمكن تفعيله عبر الكود.

## تجهيز OCR والذكاء الاصطناعي

النظام مهيّأ بنيويًا لاستخراج البيانات من المستندات دون أن يكون أي
مزوّد مفعّلًا:

- أعمدة تخزين جاهزة في `documents`: حالة المعالجة، النص المستخرج،
  الحقول المستخرجة، ومن راجعها ومتى.
- عقد مزوّد واضح في `src/modules/ocr/provider.ts`. لتفعيل الميزة
  يُنفَّذ هذا العقد بمزوّد حقيقي ويُسجَّل عبر `registerOcrProvider`،
  ولا يحتاج باقي النظام لأي تغيير.
- شاشة مراجعة بشرية تعرض ما استُخرج مع درجة الثقة، وتُتيح تصحيحه.

**حدّ مقصود:** الاستخراج يتناول بيانات وصفية فقط — أسماء وتواريخ
وأرقام. لا يتّخذ النظام أي قرار قانوني، ولا يُربط مستند بقضية إلا بعد
اعتماد مستخدم صراحةً.

## الاختبار

الاختبارات حقيقية: متصفّح فعلي على قاعدة البيانات الفعلية، لا محاكاة.

```bash
npm run dev:test   # في نافذة — موجَّه لخادم تراخيص محاكٍ
npm run test:e2e   # في أخرى
```

`test:e2e` يرفع خادم تراخيص محاكيًا محليًا (`scripts/e2e/license-stub.mjs`)
قبل تشغيل المجموعات. الاختبارات لا تلمس خادم التراخيص الحقيقي: إنشاء
تراخيص وهمية في نظام تجاري حيّ غير مقبول، والاعتماد عليه يجعل
الاختبارات تفشل عند انقطاع الشبكة.

ثلاث عشرة مجموعة تغطّي كل وحدة: المصادقة، المستخدمون والصلاحيات،
العملاء، القضايا، الجلسات والمهام والتقويم، المستندات والأرشيف،
الوكالات والعقود، الوحدة المالية، التقارير، المراسلات والتنبيهات،
والإدارة والنسخ الاحتياطي، وبوابة الترخيص.

كل مجموعة تفحص: الإضافة والقراءة والتعديل والحذف، التحقق من المدخلات،
البحث والتصفية والترقيم، حفظ البيانات فعليًا بعد إعادة التحميل، عزل
الصلاحيات، التجاوب مع الموبايل، وخلوّ الكونسول من الأخطاء.

## أدوات لائحة الدعوى

ثلاث أدوات في تبويب **«لائحة الدعوى»** داخل ملف القضية، وصفحة
**«قوالب المستندات»** في الشريط الجانبي.

### 1. قوالب المستندات

القوالب **ملك المكتب**: تُكتب داخل النظام أو تُرفع ملفات Word (.docx)
تستعملها فعلًا. النظام يملأ حقول الدمج من بيانات القضية ولا يؤلّف
نصًّا قانونيًا.

- حقول الدمج بصيغة `{{case.court}}` و`{{client.name}}` — كتالوج كامل
  بجانب المحرّر، اضغط الحقل لنسخه.
- القالب النصّي يُعرض للطباعة أو الحفظ PDF؛ وقالب Word يُنزَّل معبّأً.
- الحقل الذي لا بيانات له يظهر فراغًا معلَّمًا `__________` لا اسم
  الحقل ولا قيمة مختلقة، ويُنبَّه عليه فوق المستند قبل الطباعة.
- إدارة القوالب تحتاج صلاحية تعديل الإعدادات؛ واستعمالها يحتاج
  إنشاء مستندات.

### 2. مدقّق بيانات لائحة الدعوى

يفحص اكتمال البيانات التي توجبها **المادة 52** من قانون أصول المحاكمات
المدنية والتجارية رقم (2) لسنة 2001: اسم المحكمة، وبيانات المدعي
والمدعى عليه وصفتيهما ومحلَّي عملهما وإقامتهما، والأهلية، وموضوع
الدعوى وقيمتها، والوقائع وتاريخ نشوء الادعاء والطلبات، ووصف العين.

البنود الشرطية (الأهلية، وصف العقار) تُعلَّم «غير منطبق» لا «ناقص»،
وكل بند ناقص يحمل رابطًا لاستكماله.

> **حدّ مقصود:** فحص اكتمال بيانات لا مراجعة قانونية. النظام يقول إن
> الحقل فارغ، ولا يقول إن اللائحة صحيحة أو مقبولة. الصياغة والمسؤولية
> على المحامي.

### 3. ورقة بيانات القضية

بيانات القضية مرتّبة في ورقة واحدة بالترتيب الذي تُدخَل به عادة في
نظام ميزان، قابلة للطباعة والتصدير CSV أو JSON.

> **ليست تكاملًا رسميًا مع ميزان.** النظام مغلق ولا صيغة استيراد
> منشورة له، فما هنا ترتيبٌ للنسخ بدل التنقّل بين شاشات النظام.

## العملة

العملة تُختار من **الإعدادات ← بيانات المكتب ← العملة**، والافتراضية
**الشيكل ₪**. المدعوم: الشيكل، الدينار الأردني، الدولار، اليورو،
الريال السعودي، الجنيه المصري.

الاختيار من قائمة لا حقل حر: رمز العرض وصيغ التفقيط تُشتقّان من رمز
العملة في الخادم، فلا يصل نصّ حر من المتصفح إلى الفواتير والإيصالات،
وقيد في القاعدة يرفض أي رمز خارج المدعوم.

### التفقيط

الإيصالات تكتب المبلغ بالحروف بتمييز عربي صحيح لكل عملة:

| المبلغ | النص |
|---|---|
| 1 | شيكل واحد |
| 2 | شيكلان |
| 5 | خمسة شواكل |
| 11 | أحد عشر شيكلًا |
| 5,000 | خمسة آلاف شيكل |
| 5,250.75 | خمسة آلاف ومائتان وخمسون شيكلًا وخمسة وسبعون أغورةً |

**حدّ معروف:** المبالغ تُخزَّن بخانتين عشريتين، فالدينار الأردني يُعرض
ويُفقَّط بالقرش لا بالفلس (ثلاث خانات).

## الربط بلوحة تراخيص المصري جروب

النظام مسجَّل في لوحة التراخيص كبرنامج مستقل مثل بقية برامج المجموعة:

| | |
|---|---|
| معرّف البرنامج | `law-office` |
| الاسم في اللوحة | نظام إدارة مكتب المحاماة |
| قاعدة اللوحة | مشروع Supabase الخاص بالتراخيص |

### كيف يعمل

عند كل طلب يسأل الخادمُ دالةَ `verify_license` في اللوحة عن حالة هذه
النسخة. القرار **لا يُقرأ من قاعدة بيانات النظام إطلاقًا**، بل من رد
اللوحة مباشرة — فلا يستطيع مستخدم مسجَّل أن يفتح النظام بالكتابة في
جدول. المحفوظ محليًا في `license_state` هو المُدخلات فقط: مفتاح
الترخيص ومعرّف النسخة ورقم الجوال، ولا يعدّلها إلا صاحب صلاحية
`settings.update`.

| الحالة | السلوك |
|---|---|
| ترخيص سارٍ أو نسخة تجريبية سارية | النظام يعمل كاملًا |
| قارب على الانتهاء (≤ 14 يومًا) | شريط تحذير أعلى الصفحات |
| منتهٍ أو مفتاح غير صحيح | إغلاق كل المسارات وتحويل إلى `/activation` |
| الجهاز بانتظار موافقة | صفحة انتظار مع معرّف النسخة |
| تعذّر الوصول لخادم التراخيص | النظام يعمل مؤقتًا مع تنبيه ظاهر |

آخر سطر مقصود: تعطيل مكتب محاماة كامل بسبب انقطاع شبكة عن خادم
التراخيص ضرره أكبر من نفعه. أما الرفض الصريح فيُغلق النظام فورًا.

### التفعيل

من `/activation` — تظهر تلقائيًا لأي مستخدم عند غياب ترخيص سارٍ:

- **بمفتاح ترخيص:** يُدخله صاحب صلاحية `settings.update`.
- **بطلب نسخة تجريبية:** اسم المكتب ورقم الجوال، فيصل الطلب إلى
  اللوحة ويبدأ النظام فور اعتماده هناك.

حالة الترخيص ومعرّف النسخة يظهران دائمًا في **الإعدادات ← الترخيص**،
ومعهما زر تحديث يلتقط أي تجديد أو موافقة صدرت من اللوحة.

### متغيّرات البيئة

```
LICENSE_API_URL           رابط مشروع Supabase الخاص باللوحة
LICENSE_API_KEY           المفتاح العام للوحة (verify_license متاحة لـ anon)
NEXT_PUBLIC_APP_VERSION   الإصدار المُبلَّغ للوحة عند كل تحقّق
```

## النشر على Netlify

النظام منشور ويعمل على Netlify ضمن حساب المصري جروب:

| | |
|---|---|
| الموقع | https://masri-law-office.netlify.app |
| لوحة Netlify | https://app.netlify.com/projects/masri-law-office |
| قاعدة البيانات | مشروع Supabase مستقل `Law Office` — منفصل تمامًا عن بيانات منصة المصري |

### كيف يُبنى

`netlify.toml` يضبط أمر البناء و Node 22 ومحرك `@netlify/plugin-nextjs`،
وهو ما يجعل مكونات الخادم و Server Actions و `proxy.ts` تعمل داخل دوال
Netlify بدل بناء الموقع كملفات ساكنة. رؤوس الأمان مضبوطة في
`next.config.ts` لا في `netlify.toml`، لأن ردود Next تخرج من دالة الخادم
ولا تمرّ على قواعد رؤوس Netlify.

متغيّرا البيئة المضبوطان على الموقع:

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

### نشر نسخة جديدة يدويًا

```bash
npm run build
npx netlify deploy --prod --site masri-law-office
```

2. اضغط **Link repository** واختر مستودع GitHub والفرع المطلوب.
3. اترك أمر البناء ومجلّد النشر فارغَين — يقرأهما Netlify من `netlify.toml`.

بعدها يبني Netlify وينشر تلقائيًا مع كل دفعة إلى الفرع المختار.

## ما لم يُنفَّذ

توخّيًا للوضوح، هذه أمور مذكورة في المواصفات لم تُنفَّذ بالكامل:

- **مزوّد OCR فعلي:** البنية والعقد وشاشة المراجعة جاهزة، لكن لا يوجد
  مزوّد مُهيّأ. الاستخراج التلقائي لا يعمل حتى يُضاف مزوّد.
- **استعادة النسخة الاحتياطية:** التصدير يعمل بالكامل. الاستعادة تتم
  حاليًا من لوحة Supabase، ولا توجد شاشة استيراد داخل النظام.
- **إرسال التنبيهات خارج النظام:** التنبيهات تظهر داخل النظام فقط.
  لا يوجد إرسال بالبريد أو الرسائل القصيرة أو واتساب.
- **حماية كلمات المرور المسرّبة:** تحتاج تفعيلًا يدويًا من لوحة
  Supabase كما هو موضّح في قسم الأمان.
